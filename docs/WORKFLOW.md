# Workflow: ยืนยันทีละส่วน ลดงานซ้ำ

ใช้ต่อหนึ่ง case/revision ในทุก domain; JO เป็นข้อมูลเชื่อม ไม่สร้างเอกสารซ้ำตาม JO

**ลำดับหลัก: โจทย์สั้น → Prototype → ยืนยัน UI/behavior → สรุป Flow → Figma → AC/ FigJam**

| ขั้น | ทำให้เสร็จ | เงื่อนไขก่อนทำขั้นถัดไป |
|---|---|---|
| 1. โจทย์ | เป้าหมาย บทบาท ขอบเขต scenario และคำถามที่ยังไม่รู้; อ้างกติกากลาง/component เดิม | เจ้าของงานยืนยันขอบเขตที่จะลอง |
| 2. Prototype | ทำเฉพาะเคสเป้าหมาย พร้อม User Flow ร่างสั้น; ครอบคลุมทางหลัก ทางเลือก validation และ empty/error ที่เกี่ยวข้อง | ลูกค้ายืนยันทั้งหน้าตา การกด สิทธิ์ และผลลัพธ์ของเคสนี้; ระบุเรื่องที่ยังรอ |
| 3. Flow | สรุป User Flow, Screen Flow และ Business Flow จาก prototype ที่ยืนยันแล้ว ใช้ scenario/screen ID เดียวกัน | ยืนยันจุดส่งต่องานระหว่างบทบาท กฎ และการเปลี่ยนสถานะที่ยังค้าง; ถ้าเปลี่ยน behavior ให้แก้ prototype และยืนยันส่วนที่เปลี่ยนก่อน |
| 4. Figma | Export เฉพาะเคสที่ผ่านขั้นก่อน ตรวจ instance/key, variant, ข้อความ, currency, state และ layout เทียบ prototype | ผู้ทำตรวจความตรงครบ; ลูกค้ายืนยันเพิ่มเฉพาะส่วนที่ออกแบบหรือเปลี่ยนใหม่ ไม่ต้องอนุมัติ behavior เดิมซ้ำ |
| 5. AC → FigJam | เขียน AC ราย scenario/screen/state จาก requirement + flow ที่ยืนยัน + Figma/dump revision เดียวกัน แล้ววาง FigJam | เจ้าของ requirement/ผู้มีอำนาจยืนยัน expected result; รายการ pending ยังไม่เป็นเกณฑ์รับงานที่อนุมัติ |

## AC ทำตอนไหน

- ตอนทำ prototype: จด **เงื่อนไขสั้น** ที่ต้องลอง เช่น “ส่งกลับต้องมีเหตุผล” ใช้ช่วยรีวิวและทดสอบ ไม่ต้องเขียน AC เต็มหรือจัดบอร์ด
- หลัง prototype ยืนยัน: สรุปกฎและ flow ให้ชัดก่อน export เพื่อลดการแก้หลายที่
- หลัง Figma ตรวจความตรง: เขียน **AC ฉบับละเอียด** และอ้างหน้าจอจริง จัด FigJam ครั้งเดียวจากข้อมูล AC
- ถ้า Figma ยังไม่จำเป็น: เขียน AC จาก prototype ที่ยืนยันได้เลย แล้วเพิ่มลิงก์ Figma ภายหลัง ไม่ต้องรอเครื่องมือ
- ภาพ/dump ยืนยันสิ่งที่เห็นได้ แต่สิทธิ์ การคำนวณ API และเงื่อนไขธุรกิจต้องมี requirement รองรับ; แยก confirmed / observed / pending

## ความหมายของ Flow

- **User Flow:** ผู้ใช้ทำงานให้สำเร็จอย่างไร รวมการตัดสินใจและข้อผิดพลาด
- **Screen Flow:** หน้าจอ → action → หน้าจอ/state ถัดไป
- **Business Flow:** บทบาท → กิจกรรม → เงื่อนไข/สถานะ → ผู้รับงานถัดไป

เริ่มด้วย flow สั้นระหว่างรีวิว prototype แล้วค่อยสรุปฉบับยืนยัน; ใช้เอกสาร flow ของเคสเดียว แยกหัวข้อเท่าที่จำเป็น ไม่บังคับวาดสามผังซ้ำทุกเคส

## ประหยัด token และไม่สะสมไฟล์

1. อ่านเฉพาะเคสเป้าหมาย กติกากลาง และกติกา domain; ค้น index ของ dump ก่อนเปิดเฉพาะ component/หน้าที่ใช้
2. อ้าง ID/path แทนคัดลอก requirement, rules, component spec หรือ AC ซ้ำ; FigJam เป็นผลลัพธ์จาก AC ต้นฉบับ
3. แต่ละรอบบันทึกแค่ **เปลี่ยนอะไร / รอยืนยันอะไร / ขั้นถัดไป**; ไม่สร้างเอกสารเต็มชุดใหม่
4. เก็บหลักฐานการยืนยันหนึ่งแถวต่อขั้นใน requirement ของเคส: `ขั้น | revision | ขอบเขตที่ยืนยัน | ผู้ยืนยัน | วันที่ | หลักฐาน | เรื่องค้าง`
5. งานร่างแก้ที่เดิม; ฉบับที่ยืนยันแล้วเก็บ snapshot/tag หรือ revision ที่จำเป็น ไม่ทำสำเนาทั้ง domain
6. ข้อความ “สวยแล้ว” ยืนยันเฉพาะหน้าตา ไม่ถือว่ายืนยัน business rule หรือ AC; เรื่องค้างที่กระทบเคสต้องได้คำตอบก่อนข้ามขั้น
7. เปลี่ยนหลังยืนยัน: ตรวจผลกระทบตาม ID → แก้ prototype/flow → ยืนยันส่วนเปลี่ยน → อัปเดต Figma และ AC เฉพาะส่วนเกี่ยวข้อง

## ขอบเขตของเอกสารนี้

เป็น workflow สำหรับทำงานและบันทึกการยืนยัน ยังไม่ได้เพิ่ม stage gates ในหน้าเว็บหรือ schema
สถานะ catalog เดิม `draft / review / archived` เป็นสถานะรวม; ใช้บันทึกขั้นข้างต้นแยก และยังต้องผ่าน validator เดิมก่อนเปลี่ยนสถานะ
ลำดับนี้เป็นค่าเริ่มต้น เจ้าของงานระบุให้เริ่มจาก Figma หรือ AC ในเคสใดได้ โดยบันทึกสิ่งที่ยังไม่ยืนยันไว้ชัดเจน

## ทำ Prototype จากจอ Figma ที่ผ่าน refinement (เจ้าของงานกำหนด 13 พ.ย. 2569)

ลำดับการดูข้อมูล — ข้ามขั้นไม่ได้ · ถ้าขัดกัน **ขั้นหลังที่เป็นมติ refinement ชนะภาพในขั้นแรก** แล้วจดจุดที่ขัดไว้

| # | ดูอะไร | ที่ไหน | ได้อะไร |
|---|---|---|---|
| 1 | **จอ Figma** | `design/figma-dump/figma-*/` → `npm run render` (HTML ตรงตัว) + PNG จอจริง (frame ชื่อ `OH2 / …`) | หน้าตา โครง ค่า ข้อความ component/variant ที่ใช้ |
| 2 | **FigJam dump ของ refinement** | `design/figma-dump/<ชุด>-refinement-*/` (sticky · shape · connector ตาม section) | มติที่คุยกัน เช่น "Refinement 2026/11/12 เพิ่ม field…" · จุดที่ UI ผิด · คำถามที่ยังค้าง |
| 3 | **ข้อมูลเพิ่ม** | AC/toast เดิม · ข้อตัดสินใจขอบเขต · ภาพระบบจริง `tools/capture/captures/INDEX.md` · `design/reference/` | กติกาธุรกิจ ข้อความตรงตัว พฤติกรรมที่จอไม่ได้บอก |
| 4 | **รีวิวความเสี่ยง** | skill `senior-ux-review` + `senior-dev-review` | ตารางความเสี่ยง + คำถามถึงลูกค้า |
| 5 | **ทำต้นแบบ** | เริ่มจากโครงที่ได้จากขั้น 1 ใช้ `packages/ui` · แก้ตามมติขั้น 2 | ต้นแบบที่กดได้ |
| 6 | **เทียบภาพ** | ต้นแบบ vs PNG ทีละจอ · รายงาน % ต่าง + จุดที่ต่างโดยตั้งใจ (ตามมติ refinement) | หลักฐานก่อนบอกว่าเสร็จ |

ทำทีละ scenario (เช่น S2 = C.1–C.5) · จอที่เป็น state ของฟอร์มเดียวกันทำครั้งเดียว

## แก้ต้นแบบแล้วส่งต่อให้ครบ: prototype → gh-pages → artifact → AC ในการ์ด (19 พ.ย. 2569)

ทำตามลำดับนี้ทุกครั้งที่แก้ต้นแบบที่ลูกค้า/ทีมเห็นแล้ว · การ์ดอัปเดตเป็นขั้นสุดท้ายเพราะต้องอ้าง sha ที่ขึ้น gh-pages และภาพใน artifact ที่ตรงกัน

```
1 แก้ prototype (local) ──▶ 2 push main → Action deploy → gh-pages ──▶ 3 แคปภาพใหม่ → artifact เดิม ──▶ 4 AC + Sources + สถานะ ในการ์ด MTD
```

| # | ทำอะไร | ทำอย่างไร | เสร็จเมื่อ |
|---|---|---|---|
| 1 | **แก้ prototype** | แก้ใน `domains/<domain>/` + `src/app/(prototype)/…` · ข้อความใช้ `senior-ux-writing` · พฤติกรรมใหม่ผ่าน `senior-ux-review` / `senior-dev-review` ก่อน · รัน `npm test` `npm run check` `npm run typecheck` `npm run build` + `tests/browser/*.cjs` ที่เกี่ยว · ดูจริงที่ `npm run dev` (port 3020) | ผ่านทุก check และกดดูจอที่แก้แล้วบน local · จดสั้นๆ ว่าแก้อะไร (ใช้ต่อในขั้น 4) |
| 2 | **sync gh-pages** | commit บน `main` (`type(scope): subject (MTD-<n>)`) → push **เมื่อเจ้าของงานสั่ง** → GitHub Action `Deploy to GitHub Pages` build แล้ว push ลง branch `gh-pages` เอง (ห้าม push gh-pages มือ) · ตาม: `gh run list --workflow pages.yml -L 1` / `gh run watch` · ยืนยัน: `git fetch && git log origin/gh-pages -1 --format=%s` ต้องเป็น `deploy main <sha 7 ตัวของ commit>` | Action เขียว + เปิด https://dear-pyn.github.io/vms-plus-workspace/prototypes/overhaul/ เห็นการแก้ (hard refresh) · จด sha |
| 3 | **update artifact** | ใช้ artifact **เดิม** ของ domain (Overhaul = "เคสต้นแบบ Overhaul" https://claude.ai/artifact/6aRbuXbrciV7KeZGDgvhPM) · `Artifact read` เอาไฟล์ล่าสุด → แคปใหม่ **เฉพาะเคสที่กระทบ** จากหน้า gh-pages (ไม่ใช่ local) เข้าทางสารบัญเคส `#/cases` → แทนภาพเดิม + ใส่วันที่และ sha ที่หัวหน้า → publish ทับ URL เดิม | ภาพในหน้าตรงกับ gh-pages sha เดียวกัน · ไม่สร้าง artifact ใหม่ · ไม่มีข้อมูลคนจริง |
| 4 | **update AC ในการ์ด** | ตาม `docs/FLO-AGENT-INSTRUCTIONS.md`: comment `**เปลี่ยน AC:** <ID>` เดิม → ใหม่ · เหตุผล · หลักฐาน (sha + ลิงก์) ก่อน → แล้วแก้ description วันเดียวกัน: ตาราง AC/EC (ID เดิมไม่เปลี่ยนเลข · ตัดออกย้ายไป "ถอดออก") · Design (แถว CH) · Sources แถว Prototype = `DD/MM/25xx · <ลิงก์ gh-pages> · <sha>` + ลิงก์ artifact · บล็อกสถานะ · Change log | การ์ดบอกได้ว่า AC ไหนเปลี่ยนเพราะอะไร ดูภาพ/ต้นแบบได้จากลิงก์ในการ์ด |

**แก้แค่ไหน ทำขั้นไหน**

| ประเภทการแก้ | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| bug/หน้าตาแว้บ ไม่เปลี่ยนพฤติกรรม (เช่น โหลดแล้วจอแว้บ) | ✔ | ✔ | — (ภาพไม่เปลี่ยน) | Change log บรรทัดเดียว ไม่แตะ AC |
| ข้อความ/ระยะ/สี เปลี่ยนที่เห็นได้ | ✔ | ✔ | ✔ เคสที่กระทบ | Design (CH) + Change log · AC ถ้าข้อความอยู่ใน AC |
| พฤติกรรม/กฎ/สิทธิ์/ผลลัพธ์เปลี่ยน | ✔ | ✔ | ✔ | เปลี่ยน AC + OQ ถ้ายังไม่ชัด · ถ้าการ์ดผ่าน Customer confirm แล้ว → Stage กลับ Prototype ยืนยันเฉพาะส่วนที่เปลี่ยน |

**ข้อห้าม/ข้อควรระวัง**

- AC ที่แก้ตามต้นแบบเป็น **observed/pending** จนกว่าจะมีแถวใน Confirmation log · ห้ามเขียนว่า กฟภ. ยืนยันเพราะ "ขึ้น gh-pages แล้ว" หรือ "ลูกค้าเห็นภาพแล้ว"
- ข้อมูลต้นแบบบน gh-pages อยู่ใน Supabase ชุดเดียวที่ทุกคนใช้ร่วมกัน · ถ้าเปลี่ยนโครงข้อมูลหรือ seed ต้อง "รีเซ็ตข้อมูลต้นแบบ" ซึ่งล้างข้อมูลที่คนอื่นกดไว้ → ถามเจ้าของงานก่อน · ชุดเคสทดสอบที่สร้างจากปุ่ม Mock อยู่เฉพาะเบราว์เซอร์นั้น ไม่ขึ้น gh-pages ของคนอื่น
- push / ย้าย column / assign ทำเมื่อคนสั่งเท่านั้น · artifact เป็น private จนเจ้าของงานแชร์
- ขั้นไหนค้าง (Action แดง · ยังไม่ได้แคป) → เขียนใน `รอ:` ของบล็อกสถานะ ไม่ข้ามไปอัปเดต AC ก่อน

## เปลี่ยนใหญ่: แยก branch ให้ลูกค้ารีวิวก่อนรวม (23 พ.ย. 2569)

เปลี่ยน flow / ช่องกรอก / กติกา / แจ้งเตือน = ทำใน branch `<domain>-v<n>` (เช่น `overhaul-v2`) · แก้คำหรือหน้าตาอย่างเดียว = ทำบน main ได้

1. push branch → Action วางที่ `…/vms-plus-workspace/preview/<branch>/prototypes/<domain>/` · ข้อมูลต้นแบบแยก namespace (`NEXT_PUBLIC_PROTO_NS`) ไม่ทับฉบับหลัก
2. ให้ลูกค้ารีวิวจาก preview + artifact เล็ก "<Domain> v<n> — สิ่งที่เปลี่ยน" (เฉพาะจอที่เปลี่ยน ก่อน/หลัง) · ไม่แตะ Overview เดิม · ยังไม่แก้ AC ในการ์ด
3. ลูกค้าผ่าน → tag `<domain>-v<n-1>` ที่ main ก่อน merge → merge → อัปเดต Overview เดิมเฉพาะเคสที่เปลี่ยน + AC ตามขั้น 3–4 ข้างบน → ลบ `preview/<branch>` ออกจาก gh-pages
