# Checklist แพตเทิร์นเสี่ยง (ดูเฉพาะข้อที่จอมีจริง)

## เลือกหลายรายการ / bulk action
- ติ๊กหัวตาราง เลือกแค่หน้านี้หรือทั้งหมด → แนะนำ: หน้านี้ + แถบเสนอ "เลือกทั้งหมด N รายการ"
- ที่เลือกหายไหมเมื่อเปลี่ยนหน้า / เปลี่ยนตัวกรอง / ค้นหาใหม่ → ต้องบอกผู้ใช้ทุกครั้งที่ล้าง
- แสดงจำนวนที่เลือกตลอด · ปุ่มสั่งงานบอกจำนวน · ยืนยันก่อนทำกับหลายรายการ
- รายการที่เลือกไม่ได้ (สถานะไม่อนุญาต) → checkbox ปิด + บอกเหตุผล ไม่ซ่อนเงียบ
- เลือกเพื่อ "ใส่ในฟอร์ม" (เช่นรถในแผน) ต่างจากเลือกเพื่อ "สั่งงาน" → ฟอร์มใช้ค้นหา + รายการที่เลือก + ลบทีละรายการ

## รายการยาว / ตาราง
- เกินหน้าเดียว → ค้นหา + ตัวกรอง + แบ่งหน้า + จำนวนทั้งหมด · ตัวกรองที่ใช้อยู่ต้องเห็นและล้างได้
- ค่าว่าง "-" · ข้อความยาวตัด … พร้อมดูเต็มได้ · เรียงลำดับเริ่มต้นต้องระบุ
- จอแคบ: คอลัมน์ไหนต้องเห็นเสมอ · ปุ่ม action ไม่หลุดขอบ
- ไม่พบข้อมูล vs ยังไม่มีข้อมูล vs โหลดไม่สำเร็จ = 3 state คนละข้อความ

## การกระทำที่ย้อนไม่ได้
- ลบ / ยกเลิก / ปิดงาน / ส่งอนุมัติ → ยืนยันพร้อมบอกผลที่ตามมา · ปุ่มยืนยันใช้คำกริยาเดียวกับปุ่มที่กด
- ทำได้ไหมเมื่อมีเอกสารผูกอยู่ (PO, งานซ่อม) → ปิดปุ่ม + เหตุผล
- เหลือรายการสุดท้าย / ค่าบังคับขั้นต่ำ → บอกก่อนกด ไม่ใช่ error หลังกด

## ฟอร์ม
- ออกจากหน้าตอนแก้ค้าง → ถามก่อนทิ้ง · กดบันทึกซ้ำ → ปุ่มปิดระหว่างส่ง
- validation ตอนไหน (ออกจากช่อง / กดบันทึก) · ข้อความบอกวิธีแก้ ไม่ใช่แค่ "ไม่ถูกต้อง"
- ค่าเริ่มต้น / prefill มาจากไหน · ช่องที่ขึ้นกับช่องอื่น เปลี่ยนต้นทางแล้วปลายทางเป็นยังไง
- อัปโหลดไฟล์: ชนิด ขนาด จำนวน · ไฟล์ผิดรูปแบบเป็น validation ในจอ ไม่ใช่ toast

## ข้อความและรูปแบบค่า (กติกาโปรเจกต์)
- เงิน `1,000.00` ใช้ `packages/rules/currency.mjs` · วันที่ปี พ.ศ. (ระบบเดิมบางหน้าใช้ ค.ศ. — ถามถ้าไม่ชัด)
- คำว่า "ยานพาหนะ" ในข้อความ UI (คงชื่อประเภทรถเดิม)
- toast vs ข้อความในจอ vs modal: เลือกตามว่าผู้ใช้ต้องทำอะไรต่อ

## สิทธิ์และสถานะ
- ใครเห็นปุ่มไหน ในสถานะไหน · ซ่อน vs ปิดพร้อมเหตุผล
- badge สถานะสีและคำเดียวกันทุกหน้า · สถานะเปลี่ยนแล้วใครได้แจ้งเตือน
- สองคนแก้รายการเดียวกันพร้อมกัน → ส่งเรื่องให้ senior-dev-review
